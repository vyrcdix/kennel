# Steep — Sysadmin Guide

Quick reference for operating an existing Steep deployment.

For **first-time provisioning** (VPS, Tailscale, Caddy, systemd unit,
backups) see `docs/deploy.md`. This guide assumes that's already done
and the service is running.

> **Brand vs. codename.** The repo, env vars (`KENNEL_*`), systemd
> unit (`kennel.service`), system user (`kennel`), and DB file
> (`kennel.db`) keep the internal codename `kennel`. **Steep** is the
> user-facing brand.

The operational footprint:

| Thing | Where |
|---|---|
| Code checkout | `/opt/kennel`, owned by `kennel:kennel` |
| Built SPA | `/opt/kennel/dist` (regenerated by `npm run build`) |
| SQLite DB | `/opt/kennel/server/kennel.db` |
| Markdown content | `/opt/kennel/server/content/` |
| systemd unit | `/etc/systemd/system/kennel.service` |
| Service user | `kennel` (created with `--disabled-password`) |
| Backend port | `127.0.0.1:8421` (Caddy fronts on 443) |

## Deploying an update

Routine path: commit on your laptop, push to GitHub, then on the
server: pull, install, build, restart. ~2 minutes end-to-end.

### 1. On your laptop — push the change

```sh
git add <files>
git commit -m "<message>"
git push origin main
```

If `git push` prompts for a password, your remote is on HTTPS and
GitHub doesn't accept passwords there anymore. Switch the remote to
SSH:

```sh
git remote set-url origin git@github.com:vyrcdix/kennel.git
ssh -T git@github.com           # should say "Hi <user>! You've successfully authenticated…"
git push origin main
```

### 2. On the server — pull, install, build, restart

```sh
ssh kennel-prod                                   # or root@<server-ip>
su - kennel                                       # /opt/kennel is owned by `kennel`, not root
cd /opt/kennel
git pull
npm install
npm --prefix server install
npm run build                                     # regenerates /opt/kennel/dist
exit                                              # back to root
systemctl restart kennel
journalctl -u kennel -n 30 --no-pager
```

Expected log lines after restart:

- `Started kennel.service - Kennel server (Express + MCP).`
- `[db] applied migration: NNNN_*.sql` — only for migrations the box
  hadn't seen before. No new migration in this update = no migration
  line at all (normal).
- `[seed] skipped — KENNEL_SKIP_SEED set` — prod stays empty, no
  demo fixtures.
- `[kennel] listening on http://127.0.0.1:8421`

If you see `Error: Cannot find module …`, you skipped one of the
`npm install` lines — re-run both.

If you see a migration failure, the service won't keep running.
Migrations apply on every boot via `applyMigrations` in
`server/src/db.ts`. Roll back (next section) and investigate locally.

### 3. Smoke test

From the server:

```sh
curl -sS -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8421/api/bootstrap
```

`401` is the expected response — the service is up and enforcing
auth. `200` only happens if auth is disabled. Anything else (`5xx`,
`Connection refused`) means it didn't come up clean.

From any Tailscale-connected device, open the public URL in a
browser and confirm the change is visible.

### Stash drift on the server

If `git pull` complains about local changes, it's almost always
lockfile churn from a previous `npm install` (incidental annotation
differences, no resolved-version impact). Stash, pull, then inspect:

```sh
git stash
git pull
git stash show -p stash@{0}
```

- **Only `package-lock.json` / `server/package-lock.json` changes** →
  `git stash drop stash@{0}`. The pulled version is authoritative.
- **Build artifacts under `dist/`** → drop it. `npm run build`
  regenerates everything.
- **Anything under `src/`, `server/src/`, or `/etc/`** → stop. Don't
  auto-apply. That's a hand-edit on the server that needs reconciling.

Dropped stashes are recoverable via `git fsck --lost-found` for
~30 days, not lost.

## Resetting the web-UI password

The Steep sign-in password is hashed (scrypt) into the `settings`
row in SQLite. `KENNEL_INITIAL_PASSWORD` in the systemd unit only
seeds it on first boot — once stored, the env var is inert. To
reset, blank the stored hash and re-run the seed.

### 1. Stop the service + blank the stored credential

```sh
ssh root@<server-ip>
systemctl stop kennel
```

If `sqlite3` is installed (`apt install sqlite3` if not):

```sh
sqlite3 /opt/kennel/server/kennel.db \
  "UPDATE settings SET auth_password_hash = NULL, auth_password_salt = NULL WHERE id = 1;"
sqlite3 /opt/kennel/server/kennel.db "DELETE FROM sessions;"
```

If it isn't, do it via Node (already on the box for the service):

```sh
cd /opt/kennel/server
node -e "const Database = require('better-sqlite3'); const db = new Database('/opt/kennel/server/kennel.db'); db.prepare('UPDATE settings SET auth_password_hash = NULL, auth_password_salt = NULL WHERE id = 1').run(); db.prepare('DELETE FROM sessions').run(); console.log('cleared');"
```

The `DELETE FROM sessions` step revokes any active browser sessions
so old cookies don't keep working past the reset.

### 2. Set the new initial password

Edit the systemd unit:

```sh
nano /etc/systemd/system/kennel.service
# Find:        Environment=KENNEL_INITIAL_PASSWORD=…
# Replace the value after the = with your new password (≥ 8 chars).
# Ctrl+O, Enter, Ctrl+X
systemctl daemon-reload
```

### 3. Start the service and verify

```sh
systemctl start kennel
journalctl -u kennel -n 10 --no-pager
```

You're looking for `[auth] initial password set from KENNEL_INITIAL_PASSWORD`.
If you see `[auth] no password set — auth disabled …` instead, the
env var didn't take — confirm the spelling in the unit file and that
you ran `daemon-reload`.

Sign in with the new password.

### 4. Cleanup — don't leave the password in the unit file

Once you've signed in, change the password in-app via **Settings →
Account** to something canonical (the env-var value is meant as a
one-shot seed). Then blank the env line so the secret isn't on disk
in `/etc/systemd/system/`:

```sh
nano /etc/systemd/system/kennel.service
# Change to:   Environment=KENNEL_INITIAL_PASSWORD=
# Save, exit.
systemctl daemon-reload
```

Next restart will read the empty value; the password already in the
DB is unaffected.

## SSH access — adding a key from a new device

`/root/.ssh/authorized_keys` is the truth. Hetzner's account-level
"Security → SSH Keys" only injects keys at server-creation time and
into rescue mode — it does **not** sync to a running server.

### From an already-trusted device

```sh
ssh root@<server-ip>                              # log in with an existing key
# In a separate laptop terminal, get the new device's pubkey:
#   cat ~/.ssh/id_ed25519.pub
echo "ssh-ed25519 AAAA… new-device-comment" >> /root/.ssh/authorized_keys
```

That's it — the new device can log in immediately.

### Recovering from a fully locked-out server

(You no longer have any working key for `root@<server-ip>`.) Use
Hetzner's rescue mode:

1. Hetzner Console → click the server → **Rescue** section.
2. OS: linux64. Tick the SSH key you can match locally (or add a new
   one first via Security → SSH Keys, then come back and tick it).
3. Click **Enable Rescue & Power Cycle**. The server reboots into a
   temporary Debian rescue OS that trusts only the ticked key.
4. From your laptop, clear the old host key (rescue uses different
   `ssh_host_*` keys from the real install), then connect:
   ```sh
   ssh-keygen -R <server-ip>
   ssh root@<server-ip>
   ```
   You should land at `root@rescue:~#` with no password.
5. Mount the real disk and append your pubkey to the real
   `authorized_keys`:
   ```sh
   lsblk                                          # confirm root partition; usually /dev/sda1
   mount /dev/sda1 /mnt
   mkdir -p /mnt/root/.ssh
   cat ~/.ssh/authorized_keys >> /mnt/root/.ssh/authorized_keys
   chmod 700 /mnt/root/.ssh
   chmod 600 /mnt/root/.ssh/authorized_keys
   sort -u /mnt/root/.ssh/authorized_keys -o /mnt/root/.ssh/authorized_keys
   umount /mnt
   ```
6. Hetzner Console → server → disable rescue and reset/power-cycle.
7. After ~30 seconds, clear the rescue host key from your laptop and
   reconnect:
   ```sh
   ssh-keygen -R <server-ip>
   ssh root@<server-ip>
   ```
   You should now be at `root@debian-4gb-fsn1-1:~#`.

### Fingerprint formats

Hetzner's UI shows **MD5** fingerprints (`xx:xx:xx:…`). Match against
your local key by asking `ssh-keygen` for MD5:

```sh
ssh-keygen -E md5 -lf ~/.ssh/id_rsa.pub          # or whichever key
```

The hex part after `MD5:` is what Hetzner displays.

## Service control + logs

| What | Command |
|---|---|
| Status | `systemctl status kennel --no-pager` |
| Start / stop / restart | `systemctl {start,stop,restart} kennel` |
| Last 30 log lines | `journalctl -u kennel -n 30 --no-pager` |
| Live tail | `journalctl -u kennel -f` |
| Errors only, last hour | `journalctl -u kennel --since "1 hour ago" \| grep -i error` |
| Boot-time logs (this boot) | `journalctl -u kennel -b --no-pager` |

The service runs `npm --prefix server start`, which is `tsx
src/index.ts` — no build step on the backend, sources run directly
through `tsx`. Only the frontend gets compiled (`npm run build` →
`/opt/kennel/dist`, served by Caddy).

## Rollback

If a deploy breaks the service:

```sh
ssh root@<server-ip>
cd /opt/kennel
git reset --hard HEAD~1                           # or a specific SHA
npm install
npm --prefix server install
npm run build
systemctl restart kennel
journalctl -u kennel -n 30 --no-pager
```

If a migration corrupted the DB:

```sh
systemctl stop kennel
cp /opt/kennel/server/kennel.db.bak /opt/kennel/server/kennel.db
git checkout <last-good-sha>
npm install && npm --prefix server install && npm run build
systemctl start kennel
```

`kennel.db.bak` is written before each atomic doc write (see
`server/src/content.ts`) — not a true backup, just a same-disk
safety. For real recovery use the offsite backup configured in
`docs/deploy.md` §8.

## Sanity checks worth running monthly

```sh
df -h /opt                                        # content/ markdown grows over time
systemctl status kennel --no-pager                # service still healthy
journalctl -u kennel --since "7 days ago" | grep -iE "error|fatal" | head
ls -1 /opt/kennel/server/content | wc -l          # rough doc count
```

If `/opt` is approaching full, the SQLite + markdown footprint is
fine to relocate to a larger volume — stop the service, move
`/opt/kennel/server/{kennel.db*,content}` to the new location,
update `KENNEL_DB` in the unit file, and point a symlink (or update
the path) for the content dir.
